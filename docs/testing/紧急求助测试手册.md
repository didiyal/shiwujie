# 紧急求助 功能测试手册

> 适用版本：App 3.1.10（versionCode 15）+ 当前线上后端。编写日期 2026-09-14，行为均按当日代码实测逻辑整理。
> 姊妹篇：[志愿者求助测试手册](志愿者求助测试手册.md)。两条链路共用同一套准备环境。

## 一、功能定义

视障人士在 **AI 页点「紧急求助」**，向**同一家庭的家属**群发视频求助：所有家属手机同时响铃+震动+来电弹窗，任一家属点「接听」即与盲人进入视频通话；盲人也可在等待悬浮窗上主动取消。

关键设计（决定预期结果，先读懂再测）：

1. **家属 = 绑定了家庭的志愿者账号**，用的也是志愿者端 App。盲人账号必须已加入家庭（`blind.familyId` 非空），家庭成员 = 同一 `familyId` 下的志愿者账号列表。
2. **广播式、先到先得**：求助同时推给全部家属（信令 type=3），DB 记录只有一条；第一位接听的家属把记录置为 `HELPING`。**3.1.11 起接通后其余家属自动收回弹窗并语音播报**；两个家属同时点接听时数据库原子抢单，只有一人成功，落败者收到「已有家属接通」提示。之后的家属（弹窗未收回的残留场景）再点接听会报「对方没有在求助」。
3. **超时体系（3.1.11 起）**：
   - 盲人端 App：发出后 **60 秒**无家属接通 → **自动取消**（服务端记录置已取消，家属端弹窗自动收回）+ 语音播报「暂无家属接通，已为您取消紧急求助」，可**随时再次发起**；
   - 服务端：WAITING 记录 **60 秒**自动过期（与客户端对齐，兜底取消请求丢失）；HELPING 残留 **30 分钟**自动结束；
   - 家属端响铃：**30 秒**自动停止（弹窗保留至接听/收回）。
4. 状态机（`urgenthelp` 表 `help_status`）：同志愿者求助，`WAITING(0)` → `HELPING(1)` → `END_HELP(2)` / `FALL(3)`。

## 二、环境与准备

| 项 | 要求 |
|---|---|
| 设备 A | 盲人身份登录，**且已绑定家庭**（我的-家庭页确认已加入；未绑定的先完成绑定，不在本手册范围） |
| 设备 B | **家属**：志愿者账号，已加入 A 的同一家庭，停在志愿者端主页 |
| 设备 C（可选） | 第二个家属账号（同一家庭），测多家属竞争 |
| App 版本 | 均为 3.1.10 / code 15 |
| 权限 | **家属端首次弹窗前会申请响铃权限**（修改音频设置 + 震动），首次测试先在主页触发一次授权 |
| 响铃素材 | 手机闹钟音量（ALARM 通道）不为 0——铃声走闹钟通道，与媒体/铃声静音无关 |

**关键界面元素**：

- 盲人端 AI 页：**「紧急求助」按钮（红色）**，TalkBack 朗读"紧急求助按钮，点击向家属发起视频通话求助"。
- 发起成功后盲人端出现**紧急求助悬浮窗**：实时计时 + 「取消」按钮。
- 家属端来电：全屏来电弹窗（求助人号码 + 接听/拒绝）。

**可选·服务端核验**（SSH 端口必须是 2222）：

```bash
ssh -p 2222 root@47.112.114.139
mysql shiwujie -e "SELECT id,blind_id,volunteer_id,family_id,help_status,start_time,response_time FROM urgenthelp ORDER BY id DESC LIMIT 5;"
```

## 三、主流程时序（背下来再测）

```
盲人A AI页点「紧急求助」
   └→ 前置检查：本地状态残留则复位 → WS 已连接？
   └→ 后端：创建 urgenthelp（WAITING）→ 给该家庭全部家属发信令 type=3
盲人端：弹出悬浮窗，显示等待计时
每个家属端：响铃(30s) + 震动 + 来电弹窗
家属B 点「接听」
   └→ 后端：原子抢单（仅当记录仍为 WAITING 才置 HELPING，两人同点只有一人成功）
   └→ B 跳志愿者视频页 → 初始化成功后给 A 发 type=2
   └→ 其余家属收 type=4「已有其他家属接通」→ 弹窗自动收回 + 语音播报
盲人端：收 type=2 → 悬浮窗隐藏 → 自动跳视频页 → 通话建立
盲人 60 秒无家属接通（或主动点悬浮窗「取消」）
   └→ 走取消接口：记录置 FALL → 全部家属收 type=4 → 铃停、弹窗收回 + 播报
   └→ 盲人端悬浮窗关闭 + 播报「暂无家属接通…」（主动取消则 Toast「紧急求助已取消」）
   └→ 之后可随时再次发起
任一方点挂断（通话阶段）
   └→ 后端：记录置 END_HELP + 计时长（对端已退出时挂断是幂等成功）
```

## 四、测试用例

> 「预期」列含 App 实际 TTS 播报文案；执行时逐条打勾并记实际结果。

### A 组 · 主流程

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| E-01 | 发起求助 | A 点「紧急求助」 | 无报错；盲人端出现带计时的悬浮窗；urgenthelp 表新增 WAITING 记录 |
| E-02 | 家属端来电提醒 | E-01 后看设备 B | **响铃 + 震动**（铃 30 秒自动停）+ 来电弹窗显示求助人号码 |
| E-03 | 家属接听→接通 | B 点弹窗「接听」 | B 端 Toast「响应成功，进入视频通话」并跳视频页；A 端悬浮窗消失、自动进视频页；画面互通 |
| E-04 | 通话基础质量 | 互相对话、晃动手机 | 双向音视频正常 |
| E-05 | 盲人先挂断 | A 挂断 | A 退出；B 端「对方已离开通话」自动退出；记录 END_HELP |
| E-06 | 家属先挂断 | 重走 E-01~03 后 B 挂断 | 对称：A 端自动退出 |
| E-07 | 挂断后再次发起 | E-05 完成后立刻再点「紧急求助」 | 能正常再次发起（无「已在求助中」拦截，状态复位回归） |
| E-08 | 盲人取消求助 | 发起后、家属接听前，A 点悬浮窗「取消」 | 悬浮窗关闭 + Toast「紧急求助已取消」；B 端铃声立即停、弹窗收回 + **播报「视障人士已取消紧急求助」**；记录 FALL |
| E-09 | 家属拒绝接听 | 发起后 B 点「拒绝」 | B 端铃停弹窗关，**求助记录不动**（A 端悬浮窗继续计时）；另一家属仍可接听 |
| E-10 | 先到先得 + 其余自动收回（3.1.11 新行为） | B、C 两家属都在线，B 先接听 | B 进视频；**C 端弹窗自动收回 + 播报「已有其他家属接通，本次求助已响应」**；C 手动再点接听（如弹窗残留）报 Toast「响应失败：已有家属接通…」并播报「已有其他家属接通本次求助」 |
| E-10b | 两家属同时接听竞态 | B、C 在弹窗上**几乎同时**点接听 | 数据库原子抢单只有一人成功进视频；落败方 Toast + 播报「已有其他家属接通本次求助」，盲人只进一路视频 |

### B 组 · 超时与状态自愈（重点回归）

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| E-11 | 60 秒无接通自动取消（3.1.11 新行为） | 发起后所有家属不操作，等 60 秒 | 盲人端悬浮窗自动关闭 + **TTS「暂无家属接通，已为您取消紧急求助，您可随时再次发起」**；家属端弹窗自动收回（若铃未停则铃停）；urgenthelp 记录 FALL |
| E-12 | 取消/超时后随时可再发起 | E-11 完成后**立刻**再点「紧急求助」 | 发起成功（旧版会报"您已有一个求助正在进行"，现已消除） |
| E-13 | 杀进程不自愈卡死 | 通话中 A 直接杀掉 App 进程 → 重开 App → 点「紧急求助」 | 30 分钟内会 TTS「您已有一个求助正在进行」（服务端 HELPING 残留，由家属端挂断或等 30 分钟自愈）；**验收标准 = 不再永久卡死**：家属端挂断或等 30 分钟后必能重新发起（3.1.6 回归） |
| E-14 | 30 分钟通话残留自愈 | （可选长测）通话中双方都杀进程，等 30 分钟后 A 再发起 | 发起成功（HELPING 残留自动置 END_HELP） |
| E-15 | 双方同时挂断竞态 | 通话中 A、B 几乎同时点挂断 | 后挂的一方不报错（挂断幂等：查无通话中记录直接返回成功），状态正常复位 |
